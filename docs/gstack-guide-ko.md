# gstack 스킬 가이드 (한글)

gstack은 Claude Code에 설치되는 스킬 모음입니다. 아래 명령어는 Claude 대화창에서 `/명령어` 형식으로 실행합니다.

---

## 브라우징 & QA

### `/browse`
**언제 사용**: 페이지 스크린샷, UI 검증, 배포 확인, 사용자 플로우 테스트가 필요할 때  
**사용 예시**:
- "이 페이지 스크린샷 찍어줘"
- "사이트 열어봐"
- "이 기능 실제로 작동하는지 확인해줘"

헤드리스 브라우저(~100ms/명령)로 URL 탐색, 요소 클릭, 폼 테스트, 반응형 레이아웃 확인 등을 수행합니다.

> **중요**: 웹 브라우징은 항상 `/browse`를 사용하고, `mcp__claude-in-chrome__*` 도구는 절대 사용하지 마세요.

---

### `/qa`
**언제 사용**: 기능 완성 후 버그를 체계적으로 찾아서 자동 수정까지 원할 때  
**사용 예시**:
- "이 사이트 QA 해줘"
- "버그 찾아서 고쳐줘"
- "이거 잘 돌아가?"

3단계 티어로 동작합니다:
- **Quick**: 치명적/높음 등급 버그만
- **Standard**: 중간 등급까지
- **Exhaustive**: 미세 UI 이슈까지

버그를 발견하면 소스 코드를 수정하고 커밋까지 자동으로 합니다.

---

### `/qa-only`
**언제 사용**: 버그 수정 없이 QA 리포트만 필요할 때  
**사용 예시**: "버그 리포트만 만들어줘, 수정은 내가 할게"

---

### `/benchmark`
**언제 사용**: 페이지 성능, 로딩 속도, Core Web Vitals 측정이 필요할 때  
**사용 예시**:
- "이 페이지 속도 측정해줘"
- "성능 벤치마크 실행해줘"
- "번들 사이즈 확인해줘"

---

### `/canary`
**언제 사용**: 배포 직후 프로덕션에서 에러나 성능 이상을 모니터링할 때  
**사용 예시**:
- "배포 후 모니터링해줘"
- "프로덕션 이상 없는지 지켜봐줘"

---

### `/setup-browser-cookies`
**언제 사용**: 로그인이 필요한 페이지를 헤드리스 브라우저로 테스트하기 전  
**사용 예시**: "브라우저 쿠키 가져와줘", "로그인된 상태로 테스트하고 싶어"

---

## 코드 리뷰 & 배포

### `/review`
**언제 사용**: PR을 머지하기 전 코드 리뷰가 필요할 때  
**사용 예시**:
- "이 PR 리뷰해줘"
- "코드 리뷰 해줘"
- "머지 전에 확인해줘"

SQL 안전성, LLM 신뢰 경계 위반, 조건부 사이드 이펙트 등을 검사합니다.

---

### `/ship`
**언제 사용**: 코드를 PR로 만들어 푸시할 때  
**사용 예시**:
- "이거 ship해줘"
- "PR 만들어줘"
- "main에 올려줘"

베이스 브랜치 머지 → 테스트 실행 → 코드 리뷰 → VERSION/CHANGELOG 업데이트 → 커밋 → 푸시 → PR 생성까지 자동으로 진행합니다.

---

### `/land-and-deploy`
**언제 사용**: `/ship`으로 PR을 만든 후, 실제로 머지하고 프로덕션 배포까지 완료하고 싶을 때  
**사용 예시**:
- "머지하고 배포해줘"
- "land 해줘"
- "프로덕션에 올려줘"

PR 머지 → CI 대기 → 배포 확인 → 카나리 헬스체크 순서로 진행합니다.

---

### `/setup-deploy`
**언제 사용**: `/land-and-deploy`를 처음 설정할 때. 배포 플랫폼을 감지하고 CLAUDE.md에 설정을 저장합니다.  
**사용 예시**: "배포 설정해줘", "Fly.io 배포 연결해줘"

지원 플랫폼: Fly.io, Render, Vercel, Netlify, Heroku, GitHub Actions, 커스텀

---

## 플래닝 & 설계

### `/office-hours`
**언제 사용**: 새 아이디어나 제품 방향을 검토하고 싶을 때 (코드 작성 전 단계)  
**사용 예시**:
- "이 아이디어 어때?"
- "이거 만들 가치가 있을까?"
- "office hours 해줘"

YC 방식의 6가지 핵심 질문으로 아이디어를 검증합니다. 스타트업 모드와 빌더 모드 2가지로 동작합니다.

---

### `/autoplan`
**언제 사용**: CEO, 디자인, 엔지니어링, DX 리뷰를 한 번에 자동으로 실행하고 싶을 때  
**사용 예시**:
- "모든 리뷰 자동으로 실행해줘"
- "autoplan 해줘"
- "내 대신 결정해줘"

---

### `/plan-ceo-review`
**언제 사용**: 플랜의 비전과 스코프가 충분히 크고 야심찬지 검토하고 싶을 때  
**사용 예시**:
- "더 크게 생각해줘"
- "스코프 확장해줘"
- "전략 리뷰해줘"

SCOPE EXPANSION / SELECTIVE EXPANSION / HOLD SCOPE / SCOPE REDUCTION 4가지 모드로 동작합니다.

---

### `/plan-eng-review`
**언제 사용**: 코딩 전에 아키텍처와 구현 계획을 엔지니어링 관점에서 검토할 때  
**사용 예시**:
- "아키텍처 리뷰해줘"
- "구현 계획 확인해줘"
- "엔지니어링 리뷰해줘"

데이터 플로우, 엣지 케이스, 테스트 커버리지, 성능 등을 점검합니다.

---

### `/plan-design-review`
**언제 사용**: UI/UX 구현 전에 디자인 계획을 검토하고 싶을 때  
**사용 예시**:
- "디자인 계획 리뷰해줘"
- "UX 플랜 확인해줘"

각 디자인 항목을 0~10점으로 평가하고 10점이 되려면 무엇이 필요한지 알려줍니다.

---

### `/plan-devex-review`
**언제 사용**: API, CLI, SDK, 라이브러리 등 개발자용 제품의 DX를 플랜 단계에서 검토할 때  
**사용 예시**:
- "DX 리뷰해줘"
- "개발자 경험 확인해줘"
- "API 설계 리뷰해줘"

---

## 디자인

### `/design-consultation`
**언제 사용**: 새 프로젝트를 시작할 때 디자인 시스템(색상, 타이포, 레이아웃, 모션)을 처음부터 만들 때  
**사용 예시**:
- "디자인 시스템 만들어줘"
- "DESIGN.md 만들어줘"
- "브랜드 가이드라인 잡아줘"

---

### `/design-shotgun`
**언제 사용**: UI 컴포넌트나 페이지의 다양한 디자인 시안을 빠르게 탐색하고 싶을 때  
**사용 예시**:
- "디자인 시안 여러 개 보여줘"
- "비주얼 브레인스토밍 해줘"
- "이 UI 어떻게 생길 수 있는지 옵션 보여줘"

---

### `/design-html`
**언제 사용**: 승인된 디자인 또는 계획을 실제 프로덕션 HTML/CSS로 구현할 때  
**사용 예시**:
- "이 디자인 HTML로 만들어줘"
- "목업 코드로 만들어줘"
- "디자인 완성해줘"

---

### `/design-review`
**언제 사용**: 실제 라이브 사이트의 시각적 QA를 수행하고 디자인 이슈를 수정할 때  
**사용 예시**:
- "디자인 감사해줘"
- "시각적 QA 해줘"
- "디자인 폴리시 해줘"

실제 브라우저로 사이트를 열어 spacing, 계층, AI slop 패턴 등을 찾아 수정합니다.

---

### `/devex-review`
**언제 사용**: 개발자용 제품(docs, CLI, API)의 실제 온보딩 경험을 직접 테스트할 때  
**사용 예시**:
- "개발자 경험 실제로 테스트해줘"
- "온보딩 시간 재줘"
- "DX 감사해줘"

---

## 디버깅 & 보안

### `/investigate`
**언제 사용**: 버그나 에러의 근본 원인(root cause)을 찾아야 할 때  
**사용 예시**:
- "이 버그 디버그해줘"
- "왜 이게 안 돼?"
- "어제까지 됐는데 왜 갑자기 안 돼?"
- "500 에러 원인 찾아줘"

4단계로 진행합니다: 조사 → 분석 → 가설 수립 → 구현. 근본 원인 없이는 절대 수정하지 않습니다.

---

### `/cso`
**언제 사용**: 보안 감사가 필요할 때 (시크릿 유출, 의존성 취약점, OWASP Top 10 등)  
**사용 예시**:
- "보안 감사 해줘"
- "취약점 확인해줘"
- "OWASP 리뷰해줘"

Daily 모드(신뢰도 8/10 이상만)와 Comprehensive 모드(월 1회 전수 검사)로 동작합니다.

---

## 안전 모드

### `/careful`
**언제 사용**: 프로덕션이나 공유 환경에서 작업할 때, 파괴적인 명령 실행 전 경고를 받고 싶을 때  
**사용 예시**: "조심해서 해줘", "safety mode 켜줘"

`rm -rf`, `DROP TABLE`, `force-push`, `git reset --hard` 등 실행 전 경고를 표시합니다. 무시하고 진행할 수도 있습니다.

---

### `/freeze`
**언제 사용**: 파일 수정 범위를 특정 디렉터리로 제한하고 싶을 때  
**사용 예시**:
- "src/components 폴더만 수정하게 해줘"
- "이 폴더 밖은 건드리지 마"

---

### `/guard`
**언제 사용**: `/careful` + `/freeze`를 동시에 적용하는 최고 안전 모드  
**사용 예시**: "guard mode 켜줘", "최대한 안전하게 해줘"

---

### `/unfreeze`
**언제 사용**: `/freeze` 또는 `/guard`로 설정한 편집 제한을 해제할 때  
**사용 예시**: "freeze 해제해줘", "다시 어디든 수정해도 돼"

---

## 문서화 & 회고

### `/document-generate`
**언제 사용**: 기능, 모듈, 프로젝트의 문서를 새로 작성해야 할 때  
**사용 예시**:
- "이 기능 문서 만들어줘"
- "튜토리얼 작성해줘"
- "이 모듈 설명 문서 만들어줘"

Diataxis 프레임워크(튜토리얼/하우투/레퍼런스/설명) 기반으로 구조화된 문서를 생성합니다.

---

### `/document-release`
**언제 사용**: PR 머지 후 README, ARCHITECTURE, CHANGELOG 등을 실제 변경 사항에 맞게 업데이트할 때  
**사용 예시**:
- "배포 후 문서 업데이트해줘"
- "CHANGELOG 정리해줘"
- "docs 싱크해줘"

---

### `/retro`
**언제 사용**: 주간 엔지니어링 회고, 이번 주에 뭘 했는지 정리할 때  
**사용 예시**:
- "weekly retro 해줘"
- "이번 주 뭐 했어?"
- "엔지니어링 회고 해줘"

커밋 히스토리, 작업 패턴, 코드 품질 지표를 분석하고 트렌드를 추적합니다.

---

### `/learn`
**언제 사용**: 세션 간에 gstack이 학습한 내용을 확인하거나 정리할 때  
**사용 예시**:
- "우리가 뭘 배웠어?"
- "학습 내용 보여줘"
- "이전에 이 문제 해결한 적 있어?"

## 기타

### `/codex`
**언제 사용**: OpenAI Codex CLI로 독립적인 코드 리뷰나 second opinion을 받고 싶을 때  
**사용 예시**:
- "codex로 리뷰해줘"
- "다른 의견 들어봐"
- "codex challenge 해줘"

3가지 모드: **Code review** (패스/실패 판정), **Challenge** (코드 공격 모드), **Consult** (질문-답변)

**사용 예시**: "gbrain 설정해줘", "gbrain 연결해줘"

---

### `/gstack-upgrade`
**언제 사용**: gstack 자체를 최신 버전으로 업그레이드할 때  
**사용 예시**: "gstack 업그레이드해줘", "최신 버전으로 업데이트해줘"
